# Compiler process protocol

`merl-compiler` can run a configured executable without giving it database access. The executable reads one JSON request from standard input and writes one JSON response to standard output. Merl caps the response bytes while it reads them, validates the fields, and records the attempt before policy considers any assertion. The first-release evaluator must supply a model-backed executable; Merl does not select a model or read provider credentials for it.

The request has schema `merl.compiler-request/v1`. Its `context` contains the triggering source, a bounded recent source window from the same Issue or conversation, selected accepted objects at the interpretation basis, and the source observation cutoff. Each rendered source carries the stable entity author, the actor who made that version, and both creation and version times when known. `limits` includes input and output byte caps, a provider-facing output-token cap, assertion and context-request counts, expansion rounds, source-text bytes, source-window size, and object count. Merl records all nine limits with the run. A model wrapper must apply `output_tokens` to its provider call. Merl checks the byte and structural limits when the wrapper responds. The `object_id_prefix_v1` selector takes a deterministic bounded prefix and sets `objects_truncated` when it leaves objects out. Issue-aware selection belongs to the materialized-state work in #29.

The response has schema `merl.compiler-response/v1`. It may contain `assertions`, `relations`, `context_required`, and `unresolved`. Unknown fields fail validation. Assertions use bounded structural identifiers and cite byte spans in a captured source version. Merl derives `asserted_by` from that source's recorded author; an unknown author remains unknown. A compiler may name an attributed actor, but cannot verify that attribution or borrow the actor's authority. Free-form explanations and copied source prose have no response field. A failure records a stable code such as `output_budget` or `invalid_response`; it leaves no partial assertions. A response with `context_required` records a `needs_context` outcome. It does not satisfy required semantic coverage; a later bounded expansion needs its own run.

The request and response have generated JSON Schemas. Run `cargo run -q -p merl-compiler --bin merl-compiler-schema` to print them. The schemas come from the Rust types used by the process adapter, so an external wrapper can validate JSON without maintaining a separate copy of the field list. Merl still checks semantic limits, such as source spans and assertion counts, after decoding.

The authority first records an immutable run intent with the exact rendered context behind an erasable payload reference. The compiler receives owned context bytes and runs without borrowing the store. After it returns, the authority records a separate immutable result with the validated response behind another payload reference. A pending intent remains discoverable after a crash. Recovery loads those saved bytes instead of rebuilding context from source data; a completed identity reuses its recorded outcome. Evaluation and hindsight runs do not satisfy live semantic coverage.

For historical evaluation, import sources with `import_fixture_for_causal_replay` into a new project. That import leaves the terminal provider snapshot out of accepted state. `SequentialReplay` binds observations in source order and records the accepted revision at each step; callers cannot supply a basis revision. Start in a fresh project at revision zero, then accept earlier observations before binding later ones. An ordinary late compilation uses the basis recorded when its source was captured. Hindsight is an explicit run mode that interprets an old source against current accepted state without claiming causal replay or live coverage.
